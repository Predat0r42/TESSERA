# Черновик: блоки для визуального сборщика

© susi.su, All Rights Reserved.

Статус: дизайн-документ, не код. Реализация — отдельная фаза после
беты (см. `FUTURE.md`). Записано сейчас, пока идея свежая, чтобы не
восстанавливать контекст с нуля.

Принцип: **сборщик — это только генератор текста**. Блок → кусок
Lua-шаблона с плейсхолдерами. Результат — обычный `.lua`-файл,
который проходит через тот же `ModuleLoader`, что и любой другой.
Обратного разбора (Lua → блоки) нет и не планируется — если человек
отредактировал сгенерированный код руками, это просто файл, сборщик
его больше не трогает.

## Категории блоков

### 1. Триггеры (когда что-то происходит) — начинают цепочку

| Блок | Параметры | Шаблон |
|---|---|---|
| Когда модуль запущен | — | `function M.onStart() <тело> end` |
| Когда модуль остановлен | — | `function M.onStop() <тело> end` |
| Если время | `HH:mm` | `event.on("time.tick", function() if time.format(time.now(), "HH:mm") == "<время>" then <тело> end end)` |
| Каждую секунду | — | `event.on("time.tick", function() <тело> end)` |

### 2. Условия — вкладываются внутрь тела

| Блок | Параметры | Шаблон |
|---|---|---|
| Если [счётчик] больше [N] | counter, N | `if M.<counter> > <N> then <тело> end` |
| Если [счётчик] равен [N] | counter, N | `if M.<counter> == <N> then <тело> end` |
| Использовать [модуль] активен | module_id | `if M.<module_id>_active then <тело> end` — *(требует явного соглашения об именовании между модулями, см. "Открытые вопросы" ниже)* |

### 3. Действия — листья дерева, без вложенного тела

| Блок | Параметры | Шаблон |
|---|---|---|
| Уведомление(текст) | text | `notify.show("<модуль>", "<text>")` |
| Прибавить к [счётчику] [N] | counter, N | `M.<counter> = M.<counter> + <N>` |
| Ждать [N] [минут/секунд] | N, unit | `schedule.after(<N>, "<unit>", function() <продолжение цепочки> end)` |
| Стоп | — | `return` |
| Повторить с начала | — | вызов функции текущего цикла рекурсивно (см. пример Помодоро в истории чата) |

### 4. Управляющие блоки

| Блок | Параметры | Шаблон |
|---|---|---|
| Повторять, пока активен | — | оборачивает тело в функцию с рекурсивным self-call + проверкой `if not M.running then return end` в начале |

## Пример: как "если время 12:30 → уведомление" превращается в код

Блоки:
```
[Если время: 12:30]
  [Уведомление: "Обед"]
```

Генерируемый код (вставляется в `M.init()` или отдельную функцию,
вызываемую из `init`):
```lua
event.on("time.tick", function()
    if time.format(time.now(), "HH:mm") == "12:30" then
        notify.show("Напоминание", "Обед")
    end
end)
```

## Открытые вопросы (решить перед реализацией, не раньше)

1. **Откуда берутся имена счётчиков в UI сборщика?** Нужен блок
   "Создать счётчик [имя]" перед тем, как остальные блоки смогут на
   него ссылаться — иначе непонятно, что показывать в выпадающем
   списке у блока "Прибавить к...".
2. **Как визуально показать вложенность** (тело триггера/условия) —
   drag-n-drop с "вложенными карманами" (как Scratch/Blockly) —
   вероятно, стоит взять готовый пакет, а не рисовать с нуля.
3. **Что если человек создал блочный модуль, потом открыл в
   текстовом редакторе и всё сломал** — сборщик не должен пытаться
   его "починить" или переоткрыть в блочном виде. Просто обычный
   Lua-файл с этого момента (уже решили в разговоре — фиксирую
   здесь, чтобы не забыть при реализации).
4. **Взаимодействие между модулями через блоки** ("если [Погода]
   говорит дождь") — требует какого-то реестра "что умеет отдавать
   модуль X", которого сейчас не существует. Не проектировать
   раньше, чем появится хотя бы один модуль, который реально что-то
   такое эмиттит (см. `event.emit` в `MODULE_API.md`).

## Когда возвращаться к этому файлу

Не раньше, чем будут готовы 5-6 написанных вручную модулей — только
тогда будет понятно, какие блоки реально нужны, а какие придуманы
заранее и не пригодятся (тот же принцип, что и с Bridge API: сначала
модуль, потом функция под него, не наоборот).
