## Ближайшее (внутри плана на 2 месяца, просто ещё не сделано)

- **Настоящие push-уведомления.** `notify.show` сейчас — `SnackBar`
  через `EventBus`, не `flutter_local_notifications`.
- **Настоящие push-уведомления.** `notify.show` сейчас — `SnackBar`
  через `EventBus`, не `flutter_local_notifications`.
- **`schedule.after`/`schedule.at`.** Без них Таймер и будущий
  Будильник работают только пока приложение открыто (используют
  `event.on("time.tick")`). Обязательно нужны системные отложенные
  уведомления, а не программные таймеры — иначе ОС "убьёт" отсчёт
  при сворачивании приложения (особенно Android background limits).
- **Обработка ошибок в Lua.** Сейчас, если модуль упадёт при загрузке
  (например, забыл `module = M`), нет внятного сообщения об этом
  пользователю. План: таймаут на выполнение колбэка (~50 мс) +
  показ ошибки в UI вместо падения всего приложения (неделя 8).
- **Реальная привязка `onTap`/`onChanged` к конкретному модулю.**
  `_callLua` в `home_screen.dart` сейчас перебирает все модули по
  очереди — временное решение, описано в README.

## Следующая фаза (после беты, недели 1-9 из плана)

- **Блочный сборщик.** Дизайн блоков — `docs/BLOCKS_DRAFT.md`.
  Генерирует читаемый Lua-текст, который потом можно редактировать
  руками — без обратного парсинга.
- **Интеграции с внешними API (Telegram и др.).** Нужна
  Bridge-функция `http.request(...)` — первая, которая выходит за
  пределы локальной песочницы, и явное разрешение пользователя на
  сетевой доступ (до этого момента все модули были полностью
  герметичны). Токены/секреты для таких модулей — не в обычном
  `storage.*`, а в зашифрованном хранилище (`flutter_secure_storage`
  или аналог).
- **Маркетплейс модулей.** Публикация, рейтинг, проверка — имеет
  смысл только когда появится сообщество пользователей, пишущих
  свои модули.
- **Синхронизация между устройствами.** Если вообще понадобится —
  готовый бэкенд (Firebase/Supabase), не самодельный CRDT-протокол.

## Отвергнутые подходы (записано, чтобы не возвращаться по кругу)

- **Event Sourcing + CQRS локально** — избыточно для одного
  пользователя на одном устройстве. Обычные CRUD-таблицы.
- **Кооперативный планировщик с квантованием времени** — модулям не
  нужно вытеснять друг друга, они просто подписаны на общий тик.
- **Собственная Lua VM с capability-based security и подписями
  модулей** — песочница уже обеспечивается тем, что Lua физически не
  видит ничего, кроме Bridge-функций. Отдельный слой разрешений
  добавляется только когда появится первый модуль с сетевым
  доступом (см. выше), не раньше.
- **gRPC/GraphQL между UI и модулями** — всё в одном приложении на
  одном устройстве, простой event bus в памяти достаточен.
